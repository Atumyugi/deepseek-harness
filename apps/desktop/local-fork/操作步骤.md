## 0. 一次性准备（只做一次，做完就不用管了）


## 4. 预览（三档，按改动选）

### ① 素材级（秒级）

```powershell
start apps\desktop\local-fork\preview.html
```

静态页，不启服务。图标 128/48/32/16、托盘 ico、安装器品牌图、卸载器侧栏图、首页标题，一屏看完。换图刷新即可。

### ② 界面级（日常最常用）

```powershell
pnpm run build:artifacts          # 编整棵 client，2~4 分钟，只做一次
pnpm run start:web                # 终端打印 http://127.0.0.1:3080/?token=...
```

- **地址必须带 token**，直接开 127.0.0.1:3080 会 401。
- 端口默认 `3080`，要改：`pnpm run start:web -- --port 52838`（`$env:PORT` 无效）。
- 端口被占：`netstat -ano | findstr 3080` 找 PID 后关掉。
- 改了源码 → 再跑一次 `build:artifacts`，刷新浏览器。
- 想自动刷新：`pnpm run dev:web`（常驻监听，改一处 5~15 秒生效）。

### ③ 外壳级（真实窗口，未打包）

```powershell
cd E:\yoyiCode\deepseek-harness
$env:DSH_DESKTOP_PACKAGE_CACHE_DIR = 'E:\dsh-cache'   # 复用打包缓存，否则会联网下 Node/CPython
pnpm run dev:desktop              # 5~10 分钟（含全量编译）；编译过用 pnpm run start:desktop 秒起
```

它做的事，按顺序：

1. `build:artifacts` 编整棵 client
2. `tsc -b` + `tsdown` 编主进程 → `apps/desktop/lib/main.js`
3. 在 `apps\desktop\.desktop-build\development\` 造一份假的"已安装环境"（project 目录）
4. `preparePrimaryRuntime` 把 Node + CPython 解到 `targets\win-x64\runtime`
5. 启动 `node_modules\electron\dist\electron.exe`，把 `apps\desktop` 当 app 目录

注意三点：

- **弹的是 electron.exe，不是新生成的 exe 产物**。没有主进程 exe、没有安装包，和安装后的应用长得一样但不是一回事（进程名 `electron.exe`，任务栏图标是默认的）。
- **无热更新**。改代码要 `Ctrl+C` 重跑；只改 client 界面用 ② 那一档更快。
- **数据目录是隔离的**：`DSH_HOME` 指向 `.desktop-build\development\home`，`userData` 指向 `...\electron-user-data`。所以在 dev 里配的模型地址、登录状态，装好的正式版看不到，反之亦然。默认还会自动打开 DevTools。

> 前提：`node_modules` 里要有 electron 二进制（`dist\electron.exe` + `path.txt`）。
> pnpm 装依赖时如果没下载（离线/代理问题），dev 会报 `Electron failed to install correctly`。
> 离线补法：把 `apps\desktop\.desktop-build\targets\win-x64\electron\*` 拷到
> `node_modules\.pnpm\electron@44.7.0_*\node_modules\electron\dist\`，再写一个 `path.txt` 内容为 `electron.exe`。
> 本机已经补好了。

## 5. 打包

```powershell
cd E:\yoyiCode\deepseek-harness

# 建议先体检（秒级，不下载、不编译）
powershell -ExecutionPolicy Bypass -File apps\desktop\local-fork\build-win.ps1 -CheckOnly

# 完整打包
powershell -ExecutionPolicy Bypass -File apps\desktop\local-fork\build-win.ps1 -CacheDir E:\dsh-cache -Mirror
```

### 参数

| 参数 | 用途 |
|---|---|
| `-CheckOnly` | 只体检：Node/pnpm 版本、`.env.windows`、AppID、更新地址、工具链。不联网 |
| `-CacheDir E:\dsh-cache` | Electron/Node/CPython 下载缓存放固定盘，重装系统或换分支能复用 |
| `-Mirror` | 没有代理时让 Electron 走 npmmirror。**有代理就别加** |
| `-NoProxy` | 不自动读系统代理（纯内网/离线机器用） |
| `-DirMode` | 出目录版，跳过 NSIS，调试快 |
| `-SkipBuild` | 跳过源码编译。**只有源码一行没动、单纯想重打时才能用** |

脚本会自动从注册表读系统代理并实测，设好 `HTTPS_PROXY` / `HTTP_PROXY` / `NODE_USE_ENV_PROXY=1`。
**代理只对浏览器生效对 Node 无效**，这是最容易卡住的地方，所以别手敲 `pnpm run package:...`，用脚本。

### 为什么脚本要先编译（重要）

打包链路 `package-target.ts` **只搬运各包已经编译好的 `lib/`，它自己一行源码都不编译**。
所以「改了 `src/` 就直接打包」是本项目最容易翻车的地方：装出来的程序跑的还是旧 `lib/`，
表现就是「代码明明改了，装完却没反应」——插件没进列表、欢迎窗还在、门控没生效，全是这个原因。

现在 `build-win.ps1` 已经把 `pnpm run build:artifacts` 内置在打包前（第 5.5 步），正常跑不用管。
只有两种例外：

- 加 `-SkipBuild`：跳过编译，用现有 `lib/` 打包；
- 用 `resume-pack.ps1`：它不编译、也不重跑 `prepare:dsh`，改过源码就别用它。

想单独编译（不打包）时：

```powershell
cd E:\yoyiCode\deepseek-harness
pnpm run build:artifacts
```

> 顺带一句：`tsc -b` 只更新 `lib/types/`，`lib/index.js` 是 tsdown 从 `lib/types/` 打的。
> 所以只跑 `tsc -b` 不够，必须让 tsdown 也跑一遍（`build:artifacts` 两件都做）。

### 只重跑最后一步（前五步已成功时）

完整链路是：`build` → `prepare-runtime` → `pack` → `prepare-package-set` → `prepare:dsh` → `electron-builder`。
前五步十几分钟，只要**没改依赖、没改产品名、没换图标**，产物都还能用，可以只重跑最后一步：

```powershell
powershell -ExecutionPolicy Bypass -File apps\desktop\local-fork\resume-pack.ps1 -CacheDir E:\dsh-cache
```

它复用 `targets\win-x64\` 下的 `runtime` / `package-set` / `dsh`，从 `.env.windows` 读 6 项设置再补 unsigned 固定项，只调 electron-builder。约 3 分钟。

> **不能省的情况**：动了 `apps/cli/package.json`、`apps\desktop\scripts\prepare-dsh.ts`（第三方插件登记）、
> `productName`、图标、`brand.json` 里任何打包字段 —— 这些要经过 `prepare:dsh` 或 `build` 才会进产物，
> 必须走完整流程。

### 被「程序黑名单」拦住 `reg.exe`

失败信息长这样：

```
PROGRAM BLOCKED BY SECURITY POLICY ... reg.exe (C:\WINDOWS\system32\reg.exe)
Native installer helper compilation failed.
```

原因：编译安装器窗口 DLL 要调 `vcvars32.bat`，而 vcvars 内部用 `reg.exe` 查注册表。解法二选一：

1. 安全中心 → 命令安全 → 程序黑名单 → 把 `reg.exe` 移出去，然后跑 `resume-pack.ps1`；
2. 不动安全中心，直接在你自己的 PowerShell 窗口里跑 `resume-pack.ps1`（不经外部沙箱）。

### 产物

```
apps\desktop\.desktop-build\targets\win-x64\unsigned-artifacts\
```

安装包 + exe。右键 → 属性 → 详细信息，核对 `产品名称` / `公司` / `文件说明` 是否已是新品牌。

## 7. 报错速查

| 报错 | 处理 |
|---|---|
| `EPERM ... yarnpkg` | `corepack enable --install-directory "$env:APPDATA\npm" pnpm` |
| `Unsupported engine` | Node < 24.9，换 PATH 指向 24.x |
| `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL` | 往上看第一条真实错误，通常是网络 |
| `ECONNRESET` / GitHub 超时 | 加 `-Mirror`，或确认代理在跑 |
| `version is not defined` | `electron-builder-config.mjs` 的 `artifactName` 丢了 `\$` 转义 |
| 打包最后一步 smoke 失败 | `apps\desktop\scripts\smoke-packaged-runtime.ts` 里内嵌了 exe 名，改名要同步 |
| `PROGRAM BLOCKED ... reg.exe` | 见 5 节「被程序黑名单拦住」，改跑 `resume-pack.ps1` |
| PS1 中文乱码 | 脚本必须存成 **UTF-8 带 BOM** |
| `EADDRINUSE 3080` | 关掉旧进程，或 `--port` 换端口 |
| `Electron failed to install correctly` | `node_modules` 里没有 electron 二进制，见 4③ 的离线补法 |
| `dev:desktop` 卡在 `preparePrimaryRuntime` 下载 | 没设 `DSH_DESKTOP_PACKAGE_CACHE_DIR=E:\dsh-cache` |
| 插件页看不到预打包的插件 | 看打包日志有没有 `skipping profile bundle`，见 9.5 |

## 9. 第三方插件预打包

### 9.1 为什么必须预打包

插件管理页的"安装"= 在 `%USERPROFILE%\.dsh\profiles\desktop\` 里跑 `pnpm install`。
内网没有 npm 源，一定失败。所以要让它**随安装包发布**。

机制（两个锚点，`packages\boot\app-boot\src\profile.ts` 的 `resolveBundleDir`）：
bundle 名先从**安装包自带的 dsh**（`@deepseek-ai/dsh` 的 `package.json`）解析，找不到才查用户 profile。
判定「随包提供」的那行在 `packages\boot\plugin-manager\src\index.ts`：

```ts
const shipped = Object.hasOwn(installation.dependencies ?? {}, name)
```

**结论：把插件写成 `@deepseek-ai/dsh` 的依赖，它就会随安装包走，且优先于用户目录。**

### 9.2 默认开启（已改好，4 处）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `apps\cli\package.json` | `dependencies` 加 `"dsh-mcp-manager-plus": "0.4.4"` |
| 2 | `packages\util\official-bundles\src\bundles.ts` | `PROFILE_TEMPLATES.web.bundles` 末尾加 `'dsh-mcp-manager-plus'` |
| 3 | `packages\util\official-bundles\tests\official-bundles.spec.ts` | 那个全等断言同步改，否则测试必失败 |
| 4 | — | `pnpm install` 更新 lockfile（**要联网**） |

改完的 `web` 模板长这样：

```ts

  bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app', 'dsh-mcp-manager-plus'],
},
```

`web` 模板就是桌面端用的那个 profile，所以装完就有。

### 9.3 加更多插件

加一个插件 = **改 2 个文件 + 同步 1 个测试，然后跑 1 次安装、1 次打包**。下面以再加一个假想的
`dsh-some-plugin` 为例，完整走一遍，六步都能单独核对。

#### 第 0 步：先确认这个插件"能不能加"（3 分钟，别跳过）

九成的坑在这一步就能挡住。把包装到仓库里之前，先看它的 `package.json`。

**途径 A：从 npm 源查（打包机联网时，还没装也能看）**

```powershell
npm view dsh-some-plugin version dsh engines peerDependencies dependencies --json
```

**途径 B：已经在别的机器上装过，直接读现成的**（推荐，比查源准，看到的就是实际要打进去的版本）

```powershell
$m = "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\dsh-some-plugin\package.json"
$p = Get-Content $m -Raw | ConvertFrom-Json
"version : $($p.version)"
"dsh     : $($p.dsh | ConvertTo-Json -Compress -Depth 6)"
"engines : $($p.engines | ConvertTo-Json -Compress -Depth 6)"
"peers   : $($p.peerDependencies | ConvertTo-Json -Compress -Depth 6)"
"deps    : $($p.dependencies | ConvertTo-Json -Compress -Depth 6)"
"icon    : $([bool]$p.icon)"
```

> `-Depth 6` 不能省。`dsh` 字段有 2~3 层嵌套（`dsh.bundle.patch`、`dsh.client.inject`），
> Windows PowerShell 5.1 的 `ConvertTo-Json` 默认只展开 2 层，会把里面的值显示成
> `System.Object[]`，看着像"没有这个字段"。

`Get-Content` 报「找不到路径」说明那个插件在当前机器上其实没装成，先确认它到底在不在：

```powershell
Get-ChildItem "$env:USERPROFILE\.dsh\profiles\desktop\node_modules" -Directory | Select-Object Name
# 带 scope 的再往里看一层
Get-ChildItem "$env:USERPROFILE\.dsh\profiles\desktop\node_modules\@*" -Directory -ErrorAction SilentlyContinue | Select-Object FullName
```

把输出里的 `version` 记下来，第 1 步要用。

**一个真实的合格样本**（`dsh-mcp-manager-plus@0.4.4`，已打进当前安装包的那个）：

```
version : 0.4.4
dsh     : {"bundle":{"patch":"./cordis.patch.yml"},"client":{"platform":"web","inject":[]}}
engines :                      ← 空，表示它不用 engines.dsh，改用下面的 peers
peers   : {"@deepseek-ai/dsh":">=0.1.6-alpha.1 <0.2.0-0 || >=0.2.0-rc.1 <0.3.0-0"}
icon    : True
```

对照看：`dsh.bundle.patch` 有 → 是合法 bundle；`peers` 的区间 `>=0.2.0-rc.1 <0.3.0-0`
覆盖当前 dsh（`0.2.1-rc.3`）→ 能加载；`icon: True` → 插件页有图标。三项齐了就能加。

逐项对照（对应第 9.6 节的准入条件）：

| 检查项 | 合格的样子 | 不合格的后果 |
|---|---|---|
| `dsh.bundle.patch` | 输出里有这个键，值是文件名（如 `cordis.patch.yml`） | **不是 bundle，塞进去也不会加载**，白打一次包 |
| `engines.dsh` 或 `peerDependencies` 里的 `@deepseek-ai/dsh*` | 版本范围覆盖当前 dsh 版本 | 启动时被跳过，日志里出现 `is incompatible with dsh` |
| `dependencies` 里的原生模块 | 没有，或只有 `koffi`/`node-pty` 这类已经 unpack 的 | 内网机缺 DLL / 加载失败，表现为插件页空白 |
| 顶层 `icon` + `locale\{en,zh}.json` | 都有 | 能跑，但插件页那一栏没图标没文案，看着像坏了 |
| 是否含 `npx -y` 之类运行期下载 | 没有 | 内网跑不起来（见 9.7 第 3 条） |

`engines.dsh` 存在时**只看它**，`peerDependencies` 被忽略；没有 `engines.dsh` 时才逐个校验
`peerDependencies` 里以 `@deepseek-ai/dsh` 开头的项。当前 dsh 版本等于 `packages\boot\app-boot\package.json` 的 `version`：

```powershell
node -e "console.log(require('./packages/boot/app-boot/package.json').version)"
```

#### 第 1 步：`apps\cli\package.json` 加一行依赖

改 `dependencies`（**不是** `devDependencies`）。放在 `commander`、`js-yaml` 那一带，
即现有第三方包区域内（当前在 `apps\cli\package.json` 第 93 行附近）：

```diff
     "commander": "^15.0.0",
     "dsh-mcp-manager-plus": "0.4.4",
+    "dsh-some-plugin": "1.2.3",
     "js-yaml": "^4.3.2",
```

三个要点：

1. **必须写在这里，不能只 `pnpm add`。** pnpm 是严格隔离的，没在任何 workspace 包的
   `dependencies` 里声明的包，只会躺在 `.pnpm\` 里，**不会出现在仓库根的 `node_modules\` 顶层**。
   而 `prepare-dsh.ts` 是靠扫根 `node_modules` 顶层来发现第三方 bundle 的，扫不到就等于没装。
2. **写精确版本号，不要 `^`。** 内网是固定产物，锁死版本才能保证"N 个月后在另一台机器上打出一样的包"。
   `pnpm-lock.yaml` 会一起锁住这颗子树。
3. **不要改 `apps\desktop\package.json`。** 运行时清单的锚点是 `@deepseek-ai/dsh`（即 `apps\cli`），
   `prepare-dsh.ts` 从它生成 `dsh\package.json` 的 `dependencies`。加在 desktop 里既不进运行时清单，
   也不影响 profile。

#### 第 2 步：`web.bundles` 加一项

文件 `packages\util\official-bundles\src\bundles.ts`，加在**末尾**：

```diff
   web: {
-    bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app', 'dsh-mcp-manager-plus'],
+    bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app', 'dsh-mcp-manager-plus', 'dsh-some-plugin'],
   },
```

**顺序是有语义的，不是随笔排的。** 加载时 `loadProfileDirectory()` 按 `bundles` 的顺序逐个收集
每个包的 patch 文件，得到 `layers`，再由 `composeEntries()` 依次 `applyEntryPatches` 叠加。
**后面的覆盖前面的**，所以：

| 位置 | 含义 | 放什么 |
|---|---|---|
| 最前 | 最底层，最容易被覆盖 | `@deepseek-ai/dsh-base`（配置模型、工具、会话这些地基） |
| 中间 | 界面/应用层 | `@deepseek-ai/dsh-web-app`（Web 界面与页面骨架） |
| 靠后 | 功能插件，能改前面定下的东西 | `dsh-mcp-manager-plus`、后续新插件 |
| 最后 | 最强势，冲突时以它为准 | 你要让它**说了算**的那个 |

实际判断规则就三条：

- **新插件跟老插件不冲突** → 追加到末尾，怎么放都行。
- **两个插件改同一个配置项/同一个页面** → 想让谁生效，把谁放到**更后面**。
- **插件改的是某个已有页面的内容**（自己实现一个设置页、往侧栏塞入口） → 必须放在
  `@deepseek-ai/dsh-web-app` **之后**，否则它引用的页面骨架还没装好，patch 会落空。

> `web` 模板就是桌面端用的那个 profile（`apps\desktop\src\project-manager.ts` 里
> `WEB_PROFILE = PROFILE_TEMPLATES.web`），所以改这里等价于"桌面端默认启用"。
> `acp` / `headless` / `sdk` 三个模板**不用动**——它们不是桌面端在用。

#### 第 3 步：同步测试断言（不改必红）

`packages\util\official-bundles\tests\official-bundles.spec.ts` 第 26 行是全等断言，
`PROFILE_TEMPLATES` 一变就失败：

```diff
-      web: { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app', 'dsh-mcp-manager-plus'] },
+      web: { bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app', 'dsh-mcp-manager-plus', 'dsh-some-plugin'] },
```

同文件第二个用例会检查「`INSTALLATION_OWNED_PROFILE_TUPLES` 的每一项都必须**不等于**当前模板」，
新插件不会影响它，**不用动**。

#### 第 4 步：`pnpm install`

在**仓库根**跑（不是子目录），要联网：

```powershell
cd E:\yoyiCode\deepseek-harness
pnpm install
```

- 它会把新包装进根 `node_modules\` 顶层，并更新 `pnpm-lock.yaml`。
- 装完立刻验证第 1 步的效果，**这一步不过就别往下走**：

```powershell
Test-Path node_modules\dsh-some-plugin\package.json   # 必须是 True
Select-String -Path pnpm-lock.yaml -Pattern dsh-some-plugin -Quiet   # 必须是 True
```

- 如果包名带 scope（`@foo/bar`），上面两条同样适用，只是路径变成 `node_modules\@foo\bar`。
  `prepare-dsh.ts` 的扫描逻辑已支持 `@scope/` 子目录，不用额外改。

#### 第 5 步：重新打包

**必须走完整流程**，不能用 `resume-pack.ps1`——那个只重跑 electron-builder，
不会重编译 `lib/`、也不会重跑 `prepare:dsh`，插件进不去：

```powershell

powershell -ExecutionPolicy Bypass -File apps\desktop\local-fork\build-win.ps1 -CacheDir E:\dsh-cache -Mirror
```

（`-Mirror` 是给没有代理的机器用的；本机能走代理就去掉它，参数含义见第 5 节。）

打包前记得先彻底退出应用（否则 `EPERM: operation not permitted, unlink`，见第 5 节）。

#### 第 6 步：核对

按第 9.5 节的 ①②③ 三条命令逐条查，把里面的 `dsh-mcp-manager-plus` 换成 `dsh-some-plugin`。
三条全绿才去装机。

#### 一次加多个插件

就是重复第 1、2、3 步，注意 **`bundles` 的追加顺序**：

```diff
   web: {
-    bundles: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app', 'dsh-mcp-manager-plus'],
+    bundles: [
+      '@deepseek-ai/dsh-base',
+      '@deepseek-ai/dsh-web-app',
+      'dsh-mcp-manager-plus',
+      'dsh-some-plugin',
+      'dsh-another-plugin',
+    ],
   },
```

`apps\cli\package.json` 和 `official-bundles.spec.ts` 各自加对应的行，然后**只跑一次**
`pnpm install` 和**一次**打包。

#### 这三处不要动（改了会坏事）

| 别动 | 原因 |
|---|---|
| `INSTALLATION_OWNED_PROFILE_TUPLES` | 那是给"没有 `installationBundles` 标记的老 profile"做一次性迁移的。加了新插件不需要往这里追加，标记机制会自动带老用户跟上（见 9.9）。往里写当前模板还会让 `official-bundles.spec.ts` 的第二个用例失败 |
| `RETIRED_BUNDLES` | 这是**摘除**清单，写进去会让老 profile 主动删掉这个插件 |
| `OPTIONAL_BUNDLES` | 同一个包不要既是模板项又在这里。模板 = 装完即启用；`OPTIONAL_BUNDLES` = 随包提供但默认关（见 9.4） |

#### 出错对照

| 报错/现象 | 原因 | 处理 |
|---|---|---|
| `pnpm install` 报 `404 Not Found` | 包名拼错，或打包机没配源 | 第 0 步的 `npm view` 先确认包名存在 |
| `Test-Path node_modules\dsh-some-plugin` 是 `False` | 只 `pnpm add` 了，没写进 `apps\cli\package.json`；或 `pnpm install` 失败 | 回第 1 步补依赖行，重跑 `pnpm install` |
| `official-bundles.spec.ts` 红 | 忘了第 3 步 | 同步那一行 |
| 打包成功但插件页没有 | 90% 是没跑第 5 步的完整流程，`prepare:dsh` 没重跑 | 走 9.5 的 ①②③ 定位 |
| 启动日志 `is incompatible with dsh` | 插件 `engines.dsh` / peer 版本不覆盖当前 dsh | 换兼容版本，或在插件页对它做版本豁免 |

### 9.4 想默认关闭（装完让用户自己开）

不用 `PROFILE_TEMPLATES`，改加到同一个文件（`packages\util\official-bundles\src\bundles.ts`）的 `OPTIONAL_BUNDLES`：

```ts
export const OPTIONAL_BUNDLES: readonly string[] = [
  ...
  'dsh-mcp-manager-plus',
]
```

区别：`OPTIONAL_BUNDLES` 里的插件随包提供但**默认不启用**，插件页显示「已随包提供，点一下开启」；
`PROFILE_TEMPLATES.web.bundles` 是**装完即启用**。

### 9.5 打完怎么核对

```powershell

# ② 运行时清单有没有"声明"它（决定插件页是否把它当随包提供列出来）
```

桌面端 `files` 配置里有 `{ from: buildPaths.dsh, to: 'dsh' }` 整树进 asar，所以①有就等于进包了。

> （`koffi`、`node-pty`、`sherpa-onnx` 之类二十来个），普通 JS 包全在 `app.asar` 内部，
> 资源管理器打开看不到。①有、②有，就没问题。

### 9.6 哪些插件能这么干（准入条件）

| 条件 | 说明 |
|---|---|
| `package.json` 有 `dsh.bundle.patch` | 指向一个 `cordis.patch.yml`，没有就不是 bundle，塞进去也不会加载 |
| 顶层 `icon` + `locale\{en,zh}.json` | 插件页的显示元数据，缺了能跑但界面是空的 |
| peer 版本覆盖当前 dsh | 如 `>=0.2.0-rc.1 <0.3.0-0` |
| 依赖能离线满足 | 不能有需要编译的原生模块，或必须正确 unpack |

### 9.7 三个坑

1. **打包机要能连 npm 源**。`prepare-dsh.ts` 在打包阶段用 `pnpm install` 把外部依赖解析进 asar。
   装到内网后不需要网，但**打包那次**需要（或配镜像）。
2. **老 profile 靠「下发标记」自动跟上，不需要改代码**。profile 的 `package.json` 里现在多一个
   `dsh.profile.installationBundles`，记录安装方上次下发的列表。只要用户没自己改过 `bundles`，
   每次升级都会对齐到新模板——**加多少个插件都跟得上**，详见 9.9。
   比这更老的 profile（没有这个标记）走 `INSTALLATION_OWNED_PROFILE_TUPLES` 的精确元组兜底。
3. **MCP 插件本身不解决服务器问题**。它只是配置页；它拉起的 MCP server 如果靠
   `npx -y @modelcontextprotocol/server-xxx`，内网照样跑不起来，要换成本地二进制路径。

### 9.8 装完插件页看不到，按这四条查

| 现象 | 原因 | 查法 |
|---|---|---|
| 插件包里根本没有这个目录 | 只改了 `src`，没重编译 `lib`。打包用的是各包的 `lib/`，不是 `src/` | 9.5 的 ① |
| 有文件但插件页不列它 | 运行时清单 `dsh/package.json` 没声明它 → 插件页的候选名集合里没有它 | 9.5 的 ② |
| 清单里有、装完 profile 也没有它 | profile 是老机器上的旧文件。`initProfile()` 不覆盖已存在的 profile，桌面端以前没接迁移逻辑 | 9.5 的 ③（现在会自动迁移，见 9.9） |
| profile 里有、插件页仍不启用 | 用户自己改过 `bundles`，迁移会尊重这个选择 | **插件页里仍有它，点一下就能开**（见 9.9） |

第一条最容易误判：`lib/` 没重编译时，`package-target.ts` 会把**旧的** `lib/` 原样搬进 asar，
文件、清单、profile 三处看起来都对，但插件代码是旧的或者根本没进去。判断办法只有一个——
看打包前有没有跑过编译（现在 `build-win.ps1` 第 5.5 步会强制跑，见第 5 节）。

第三条最容易误判成第二类：插件其实已经打进包了（`app.asar` 里搜得到名字），但目标机的
`profiles/desktop/package.json` 还是旧的两项。这时问题不在包里，在 profile。

第二条最容易漏：`dsh/package.json` 的 `dependencies` 原先**只由 workspace 包组成**
（`prepare-dsh.ts` 里由 `packageSet.packages` 生成），第三方的 bundle 即使被 pnpm 装进了
`node_modules`，也不会出现在这份清单里，于是插件页永远不会列它。现在改成
「扫描 `node_modules` 顶层里所有声明了 `dsh.bundle.patch` 的包，补进 `dependencies`」，
所以第三方 bundle 只要装进来就会被登记。

### 9.9 以后每加一个插件，老机器会不会跟上

**会。** 这是靠 profile 里的 `dsh.profile.installationBundles` 标记做到的，不需要你每次去改代码。

原来的机制只认「精确等于某个历史列表」，所以天然只能升级一次：第二次加插件时，老机器的列表
既不等于第一版也不等于第二版，就永远卡住了。现在的规则：

| 用户做过什么 | 升级后表现 |
|---|---|
| 从没动过插件开关 | `bundles` 对齐新模板 → **新插件自动启用** |
| 自己禁用过某个默认插件 | 列表被改过 → **不动**，尊重用户选择（新插件也不强推） |
| 自己手动加过插件 | 同上，不动 |
| 没改过、但列表恰好等于模板 | 顺手写入标记 → 之后也进入自动跟随 |

所以你加插件的动作还是那 4 步（9.2 / 9.3），**不用再往 `INSTALLATION_OWNED_PROFILE_TUPLES` 里追加任何东西**。

#### 桌面端为什么要单独接一次

上面这套原本只走 Host 的「按名字取模板」（`web` / `headless` / `acp` …）。但桌面端的 profile 目录叫
`profiles/desktop`，`PROFILE_TEMPLATES` 里**没有这个名字**，所以从来不走迁移；而 `initProfile()` 对
**已存在**的 profile 又是一个字节都不改的：

```ts
if (!existsSync(manifestPath)) { /* 只有不存在时才写模板 */ }
```

两件事叠在一起的结果就是：老机器重装新包，`bundles` 永远停在旧的那两项，新插件永远出不来。

现在 `DesktopProjectManager.applyRelease()` 在 `initProfile` 之后补了一次
`alignInstallationOwnedBundles(profile, WEB_PROFILE.bundles, INSTALLATION_OWNED_PROFILE_TUPLES.web)`——
和 Host 用的是同一个函数、同一套规则，所以桌面端也进入自动跟随。

老机器上确认一下就行：

```powershell
# 有 installationBundles → 以后自动跟；没有 → 看下面两条
Get-Content "$env:USERPROFILE\.dsh\profiles\desktop\package.json"
```

- **没有标记、`bundles` 是 `[base, web-app]`** → 装上新包启动一次就会自动补上插件并写入标记，什么都不用做
- **没有标记、`bundles` 已被手工改过**（例如插件页关过东西） → 不会自动迁移；想恢复默认就删
  `profiles\desktop` 重建（第 11 节 B 档），或者手工把插件名加进 `bundles`

> 为什么不做成「缺什么补什么」：那样用户关掉的插件会在每次启动时自己弹回来，比不生效更烦人。
> 判断「用户改过没有」只能靠标记，这也是它存在的唯一理由。

## 11. 老机器重置配置（升级后插件没生效时）

装新包之前跑过旧包的机器，profile 已经存在。**新版启动时会自动迁移**（见 9.9），
所以先确认一句：启动后插件已经出现 → 本节整节不用做。

只剩两种情况需要手动处理：

1. 用户**自己改过** `bundles`（插件页关过东西、手动加过插件）——迁移会尊重这个选择，不强推新插件；
2. profile 本身已经损坏，或者你就是想验证「全新装出来是什么样」。

按档位选，从轻到重：

| 档 | 删什么 | 丢什么 | 用在哪 |
|---|---|---|---|
| A 手工加（不删） | 只改 `profiles\desktop\package.json` 一行 | 什么都不丢 | 只想让插件出现，配置全部保留 |
| B 删 profile | `%USERPROFILE%\.dsh\profiles\desktop` | 自定义模型 provider 配置、插件启停状态 | 想验证"装完就有"，会话和密钥保留 |
| C 彻底重置 | `.dsh` 整个 + `%APPDATA%\XiaoGuang Agent` | **全部**：会话、附件、凭据、偏好 | 换人交接、机器要重交付 |

> 三档都要求**先完全退出应用**：关窗口不够，还要右键托盘图标退出，或任务管理器里
> 结束 `XiaoGuang Agent.exe` / `electron.exe`。文件被占用时删除会只删一半。

### A 档：只加一行（推荐先试这个）

```powershell
notepad "$env:USERPROFILE\.dsh\profiles\desktop\package.json"
```

在 `dsh.profile.bundles` 数组末尾加一项，保存，重启应用：

```json
"bundles": [
  "@deepseek-ai/dsh-base",
  "@deepseek-ai/dsh-web-app",
  "dsh-mcp-manager-plus"
]
```

### B 档：删 profile（保留会话与密钥）

```powershell
# 1) 备份，万一要回退
Copy-Item "$env:USERPROFILE\.dsh\profiles\desktop" "$env:USERPROFILE\dsh-profile-backup-$(Get-Date -f yyyyMMdd-HHmm)" -Recurse

# 2) 删掉，下次启动按新模板重建
Remove-Item -Recurse -Force "$env:USERPROFILE\.dsh\profiles\desktop"
```

保留在 `.dsh` 根目录、不受影响的有：`sessions`（会话）、`attachments`（附件）、
`.credentials.yaml`（API 密钥）、`storages`。但 `cordis.patch.yml` 里的自定义 provider
路由定义在 profile 内，会一起没——重进应用后到 **设置 → 模型** 重填一次地址即可
（密钥还在，不用重填）。

### C 档：彻底重置

```powershell
# 0) 先备份整个 .dsh（约几百 MB，看会话多少）
$stamp = Get-Date -f yyyyMMdd-HHmm
Copy-Item "$env:USERPROFILE\.dsh" "$env:USERPROFILE\dsh-full-backup-$stamp" -Recurse

# 1) dsh 数据（会话、附件、凭据、profile、缓存）
Remove-Item -Recurse -Force "$env:USERPROFILE\.dsh"

# 2) Electron 外壳数据（窗口状态、快捷键、缓存；不含会话）
Remove-Item -Recurse -Force "$env:APPDATA\XiaoGuang Agent"
```

`%APPDATA%\XiaoGuang Agent` 里没有业务数据，只有 `Cache`、`Local Storage`、`Preferences`、
`keybindings.json` 之类，删了就是回到"第一次打开"。

### 卸载后查残留

卸载器**不会**删 `.dsh` 和 `%APPDATA%\XiaoGuang Agent`，这两处要手动清。逐一确认：

```powershell
Test-Path "$env:USERPROFILE\.dsh"
```
